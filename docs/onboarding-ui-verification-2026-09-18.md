# Onboarding implementation and frontend evidence

## Implemented

- Signup collects a required business name, transactionally creates the account and its first real inventory with that business name, then opens source selection. The inventory name remains editable inline; it is not derived from the owner's personal name. Further inventories still have an explicit creation form and a separate-inventory explanation.
- Onboarding has three visible choices in this order: files, supported system connection, manual product entry. Each states its prerequisite. A spreadsheet can be dropped directly on source selection; choosing a file also starts upload without another navigation decision.
- Imports still use the existing real parser, staged reconciliation and explicit activation approval. Reducing entry steps does not bypass migration safety checks.
- Skip opens a usable empty app. Empty pages retain an add-source prompt. The first-run empty home and source chooser have no invented previous-page link. The additional-inventory form has one back link, a genuine example placeholder and no real/test radio.
- Sample exploration creates actual sample products and opening movements in a separate, labeled synthetic inventory. Repeating load reopens that inventory. Clear deletes only this disposable container, including anything subsequently added there, and returns to the unchanged real inventory when it exists. Suggestions can be dismissed persistently; Settings still offers exploration.
- Each sample has its own ownership and origin marker. Deleting its original real inventory does not strand the sample without a clear action. Another account cannot clear it. Real inventories cannot be cleared through this endpoint.
- Empty synthetic test inventories can be created from Settings. Neither test nor sample data can be converted to real. Email attachment setup is an ongoing Settings ingestion feature; it is not an onboarding source choice. Legacy ingestion/multiple-file bookmarks remain compatible.
- Desktop cards fit within the tested 1280 by 800 viewport. On narrow screens, all three choices remain present, an explicit three-choice message signals the options below, and the tested 390-pixel layout has no horizontal overflow.

### Remaining boundaries

### Zero-inventory account correction

The initial signup-only fix did not cover previously created accounts that had never received an inventory. Their authenticated `/inventories` screen still asked them to create one. Both `/inventories` and `/inventories/new` now initialize the first blank real inventory transactionally for these accounts and redirect directly to source selection. Since an older account has no stored business name, its initial name is the editable `My inventory`, not an invented company name or a personal name passed off as a business name. New signup continues to use the required business name.

An account-level first-inventory marker survives inventory deletion. Opening the list must not silently recreate an intentionally deleted inventory or restore a revoked membership; bootstrap also checks existing membership and ownership. Existing owned inventories are backfilled into this marker on database startup. Repeated initialization creates no duplicate inventory and grants no automatic operational authority.

`artifacts/onboarding-zero-inventory-account-2026-09-18.log` passes all 40 targeted checks: eight browser tests including actual sign-in of a legacy zero-inventory account, automatic handoff, inline rename and refresh/repeat safety, plus 32 supplemental account/permission/sample/deletion checks. The only legacy precondition is a test account created without an inventory; the transition and assertions run through the frontend. This onboarding correction does not implement the four autonomy/pilot requirements below.

Additional correction validation passed all 13 registration/security tests, including missing, blank and overlong business names leaving no partial account or inventory (`artifacts/onboarding-business-name-validation-2026-09-18.log`).

- Samples currently consume the existing inventory allowance (three inventories on the current free plan). At the limit, loading a new sample reports the quota failure rather than altering or filling a real inventory. No plan, billing or subscription behavior was added.
- The original onboarding-only changes did not grant operational authority. The subsequent explicitly confirmed own-data proposals, batch approvals and in-app daily digests are described below. An empty signup or small sample cannot substantiate a weekly dollar limit or a claim of 65 percent automation.
- Live Stripe/carrier/mailbox/accounting qualification with friendly businesses remains a separate, permissioned release gate. This local frontend run sends no external email, buys no postage and transfers no money. Existing connection screens are not proof that a particular real provider has been qualified.
- A production miss-learning loop needs real operator transcripts, triage, explicit expected outcomes and permanent regression tests. The subsequent durable miss intake and owner review support triage, not automatic code repair or silently learned execution rules.
- Business PostgreSQL migration and deployed restoration/load/rollback gates remain unfinished. Completing onboarding does not make the entire product production-ready.

## Onboarding clarity and autonomy follow-through

The source page no longer renders the global empty-inventory banner or an Add a source link to itself. It has a compact Add your inventory heading, an editable prefilled name and three cards. File selection/drop starts upload immediately; Retry upload appears only on an upload error. Dismiss hides the optional sample suggestion in place, while Skip opens a light, readable empty home. The home retains real operational work if an inventory has no products but does have pending or running actions; the welcome screen must not hide those actions. Desktop source and empty-home screenshots were visually inspected, and browser assertions check heading contrast against the white background.

### Authority from recorded business data

`src/autopilot/authority-proposal.js` proposes purchasing only for active usual suppliers with at least three priced USD orders actually placed in the last 90 days. It excludes orders with unknown prices or additional charges. The proposed per-order and rolling-seven-day limits come from observed history, and the product scope is the previously purchased SKUs. Viewing the proposal grants nothing. Confirmation re-reads and hashes current evidence inside a transaction; stale proposals and already-configured inventories cannot silently widen authority.

For eligible usual suppliers, the same confirmation can approve routine supplier communication using their saved recipient and watched Gmail/M365 mailbox. A connected, unpaused mailbox with stored credentials and MAIL_SEND capability is required. The supplier-specific PO amount limit is displayed. The current PO value, currency, recipient and mailbox are rechecked before automatic execution. An initial PO approved before this sending grant needs individual review; follow-ups require a provider-confirmed original message.

A connected carrier with stored credentials and at least three recorded successful, non-reversed USD label purchases for a carrier/service can support a label proposal. The displayed per-label cap is the largest recorded price for that service. Enabled accounting must also use USD for this proposal. Confirmation saves the specific carrier/service rules and a USD monetary grant. Dispatch rechecks the current active rule, promised date, packed/readiness state, accounting base currency and matching quote value/currency; quotes older than 15 minutes require requoting. Verification compares the actual charge, currency and service with the authorised quote, and reads back the required balanced, same-currency postage entry when accounting is enabled. An incompatible currency is not silently posted with an invented exchange rate. A closed-period/posting failure or unexpected carrier charge becomes a visible exception without buying a second label. A purchased label is not a physical handoff, and does not move inventory. Payments are never authorised by this setup.

The new generic grant currency column is added to existing SQLite databases, not merely declared for fresh databases. Domain adapters cannot bypass explicit generic monetary/currency bounds or a revoked grant. Automatic PO preparation, monetary revalidation and completion recording use an immediate SQLite transaction to serialize the purchase-budget check. Existing universal provider aggregate daily-budget concurrency remains a separate release risk; these proposals do not claim or grant an aggregate shipping/email spending budget.

Recorded history and connected credentials are prerequisites, not live-provider certification. No 65 percent automation claim is substantiated. Unsupported currencies or insufficient history produce no guessed limit. An eligible first-run inventory displays the suggested amounts and suppliers directly on its Brief, with Review and confirm limits opening the full evidence and one explicit confirmation. Settings / Automatic work also exposes this review. No proposal is imposed during empty signup, and already-configured inventories avoid re-reading historical evidence on every Brief request.

### Approvals, digests and miss intake

Five similar approvals by the same actor, for the same supplier or transfer direction and still-authorized, executing, verifying or completed statuses, produce one pending operating-instruction suggestion. Failed/cancelled approvals are excluded. Purchase suggestions require current priced USD purchase documents matching the approved amount, exclude additional charges, and bind the previously approved products and USD limit into the resulting policy. The suggestion does not grant authority until the owner reviews and confirms its exact versioned policy. Browser acceptance also opens the suggestion, approves it explicitly and verifies the remembered-active state.

`src/autopilot/daily.js` and `/autopilot/daily` provide verified completions for a selected UTC calendar day, current pending decisions, unfinished work, separately labelled provider operations and supplier message states. Batch approval preflights every selected snapshot and business document in one transaction before approving any selection. Execution then rechecks business state and reports each result separately. Missing references remain visible and unselectable; stale/foreign selections cannot partly approve a batch. Internal PO approval is explicitly distinguished from supplier email acceptance, which itself is not proof of inbox delivery or receipt.

The regular scheduled worker records a previous-day in-app digest once per inventory, including when operational execution is paused. Generation time is stored; current pending counts are not presented as reconstructed historic counts. This is not emailed delivery. The port-4000 integration-verification server intentionally does not run operational workers: an empty digest history honestly says no automatic snapshot exists yet, rather than claiming the local worker is running.

`src/manager/misses.js` and `/autopilot/misses` store exact questions, actual and expected behavior, and owner review notes. A matching Ask intent is linked only for the same inventory/user/question. Staff can view only their own reports; administrators can review inventory reports. REVIEWED is not FIXED or VERIFIED. Actual developer fixes and permanent passing regression tests are still required to close real-owner misses; no arbitrary feedback becomes an execution rule automatically.
