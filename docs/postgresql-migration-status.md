# PostgreSQL migration status, September 23, 2026

## Actual boundary

`src/server.js` now selects the native PostgreSQL web process whenever `FOUNDRY_DATABASE_URL` or `DATABASE_URL` is present and refuses SQLite startup entirely under `NODE_ENV=production`. Local development without a PostgreSQL URL still enters the explicitly named `src/sqlite-server.js`. The PostgreSQL process runs authentication, inventory creation/switching, onboarding, locations, the product catalogue, stock movements, transfer custody, purchasing, receiving, supplier invoices/payments, customer orders, fulfillment, customer payments, customer and supplier returns, Ask StockChief, connections, shipping, opening-inventory imports, bounded transfer-versus-buy autonomy, Brief, Needs You, activity, Money, accounting reports, tenant-scoped operations readiness and a scoped inventory API without opening SQLite. The deployment gate remains blocked until managed-staging browser, recovery, rollback, failure and load certification passes.

The migration foundation is now materially further along: a clean PostgreSQL 17 database can create the complete constrained StockChief business schema, atomically import a file-backed SQLite business, rebuild derived catalogue/search projections from canonical records, reconcile every table and critical business total, roll back a failed cutover without leaving business rows, and safely recognize an exact replay. Native PostgreSQL quantity, variant, lot and serialized inventory execution now preserves the append-only ledger, idempotency and concurrent oversell protections. A full local rehearsal against the 4.29 GB operating database completed on September 23, 2026 with 271 tables, 80,269 SKUs and 40,183 movements reconciled and balanced. This is the production-selected backend, but it does not yet provide feature parity for every legacy operational family.

## Remaining engineering, not just credentials

1. Port the remaining synchronous callers to awaited, transaction-scoped services. The full-page catalogue/onboarding UI, global search, selling-price and purchase-cost approvals, forward planning, Ask StockChief, supported free-form standing instructions, governed connector-mapping repairs, connections, normalized connector events, business-mail capture/replies/polling/webhook wake-ups and push renewal, signed Shopify/Square/WooCommerce/Clover commerce webhooks, durable provider catalogue discovery and exact mapping, worker-owned outgoing email, provider-hosted payment requests, deposits, payment completion and refunds, shipping, opening-inventory imports, customer and supplier returns, bounded transfer-versus-buy autonomy, canonical autonomy attention, warehouse waves, core projections, accounting reports and accounting-export provider effects are now native in the PostgreSQL web process. Autonomy for the remaining operational action families and unsupported standing-instruction families still need native ports. Do not hide this behind a synchronous-looking PostgreSQL adapter.
2. Native inventory, purchasing, receiving, sales, supplier-invoice, payment and fulfillment-wave execution now enforce the same per-membership permission model as the SQLite product. Remaining PostgreSQL ports must preserve that rule. A 24-order concurrent reservation and fulfillment workload now proves deterministic balance locking, exact backorders, no overselling, zero lost allocations, reconciled costing and balanced accounting under contention; managed staging still needs the deployed version of this workload.
3. The default production web launcher now selects PostgreSQL and fails closed without its database URL, HTTPS public origin and stable shared secrets. Port the remaining routes before treating that launcher as full feature parity; keep the PostgreSQL worker as a separately deployed process.
4. The native runtime scheduler now handles sessions, interrupted imports, stale connectors and interrupted provider effects. Postage purchase, outgoing email, hosted customer-payment requests, provider refunds and accounting exports use the durable external-effect worker and stop on ambiguous outcomes. Preserve this discipline for every remaining external action rather than retrying uncertain effects blindly.
5. Run the completed cutover/reconciliation process against the managed staging database. The full isolated local rehearsal has passed; no customer data has been moved to the managed database.
6. Local PostgreSQL backup/restore, worker throughput, HTTP soak and shared release checkpoints now pass. Repeat those gates against managed staging, prove the restored business through its frontend, and capture actual hosting rollback/failover evidence.
7. `render.yaml` now defines separate PostgreSQL web and worker services in the existing `My project` / `Staging` environment, binds both to the existing `stockchief-staging` private connection, runs locked migrations before deployment, uses generated shared internal secrets, checks `/readyz`, accepts Render's immutable commit identity and keeps automatic deployment off. Render CLI 2.28.0 validated the Blueprint against the StockChief workspace on September 24, 2026 with four planned actions and zero errors. Syncing it would create two paid `1c-2g` services ($50/month new recurring compute) and therefore still requires explicit cost approval. Managed business queries and deployment have not occurred yet; see `docs/render-staging-deployment.md`.
