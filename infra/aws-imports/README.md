## Data flow

1. An authenticated operator creates an upload intent. Existing capability and storage admission checks run first. The server chooses the inventory-scoped S3 key.
2. A ten-minute signed POST binds the exact byte count, SHA-256, upload ID and inventory metadata. The browser sends the original straight to the private S3 bucket.
3. Completion checks S3's checksum/metadata and freezes its version ID. A transaction creates the ordinary saved-upload record, durable job and outbox intent together. Repeated completion converges on the same job.
4. The Render worker publishes committed outbox entries to SQS. A failed publish leaves the entries for retry. Queue messages contain only wake signals; they cannot supply a tenant, grant approval or execute stock changes.
5. The Fargate worker wakes and claims eligible jobs through the existing PostgreSQL queue. Periodic bounded polling recovers a missing wake. Account import concurrency, durable leases and all existing commercial checks remain authoritative.
6. Tabular source reading uses `import.analyse-source.aws`. PDF, image and handwriting reading remain on the existing Render reader, preserving their provider configuration and billing controls. Approved execution uses the existing `import.execute-approved` handler.
7. Large validated row batches use streaming `COPY` into a transaction-local temporary table, then a scoped `INSERT SELECT` into the existing import evidence table. Live stock, prices, costs and journals use the existing guarded application engine. COPY never writes balances directly.
8. Stock changes still require the approved frozen plan, the catalogue session lock, plan/SKU locks and compare-and-set checks, nonnegative guarded balances, idempotent batch receipts and accounting verification. An interrupted task resumes from durable committed progress.

Original source snapshots remain in the existing PostgreSQL evidence archive. S3 originals are temporary transport copies with seven-day lifecycle expiry; upload intents expire after 24 hours. This intentionally preserves the current source-review and historical evidence contract. It is **not** a claim that this release removes historical database evidence storage. External archive/retention changes need their own verified migration.

## Infrastructure and access

`template.json` is generated by `node infra/aws-imports/build-template.js` and validated with `cfn-lint`.

- One private, encrypted, versioned source bucket; exact-origin CORS and TLS-only policy. Retained if the stack is deleted.
- One encrypted SQS queue and one dead-letter queue, with backlog/DLQ alarms.
- One ECS/Fargate service. Each task has 1 vCPU, 2 GiB RAM, a five-connection database pool and one import slot. The task count is explicitly limited to 0, 1 or 2; it defaults to zero. This version does not pretend wake-queue depth measures the full business-job backlog, so it does not autoscale on that misleading signal.
- A private subnet, NAT gateway and fixed outbound IPv4 address. No inbound worker port or public task IP. S3 traffic uses a gateway endpoint.
- Database outbound traffic is restricted to the approved database /32. HTTPS is used for AWS endpoints. Render must allow only the NAT /32; do not allow the entire internet.
- `sslmode=verify-full` is mandatory for the external database URL. A Render private hostname is rejected. Do not disable TLS verification.
- ECS task role reads source versions and receives/deletes queue wake signals. Execution role can retrieve only the designated database secret. A separate Render application identity can upload/check sources and send queue signals. The template creates **no access keys**, and writes no secrets to outputs.
- Container runs as the unprivileged `node` user. Temporary parsing files use ephemeral task storage. Logs retain 14 days and must not include source rows, credentials or message bodies. ECS replaces exited tasks. SIGTERM drains the current handler; forced termination preserves durable checkpoints.

Use a dedicated application database role, not a migration/database-owner credential. Its required DML permissions must be qualified against the guarded engine. Store the verified external connection URL only in the approved AWS Secrets Manager destination after authorization. The existing production database currently has external access disabled; this branch does not change that.

## Deployment sequence — requires concrete resource/cost approval

1. Complete sign-in, verify the project identity/plan, and load the official AWS skills. Confirm us-east-2 and the project spend limit. Inspect existing resources rather than replacing them.
2. Review this stack, the immutable candidate commit, cost worksheet, secret destination, fixed-IP database access and dedicated database role. Obtain approval before creating billable resources or enabling external database access.
3. Preview a CloudFormation change set, with `WorkerCount=0`. Do not execute it as part of validation. Creating the stack starts NAT charges even with no workers.
4. After approval, create the resources. Bootstrap with an image URI and `WorkerCount=0`; build `infra/aws-imports/Dockerfile`, push to the created ECR repository, resolve the immutable digest and update `WorkerImage`. No service starts until explicitly scaled above zero.
5. Prepare the dedicated database role and approved secret. Verify the database's actual region and measure cross-provider latency: an Ohio worker is not automatically close to a Render database in another region. Apply migration 539 through the reviewed normal release process, never from worker startup.
6. Allow only the fixed NAT IP on the intended qualification database. Never open production or copy customer data merely to run a benchmark. Start one import worker and verify TLS, permissions, leases, graceful interruption and recovery using synthetic records.
7. Deploy the application code with `STOCKCHIEF_IMPORT_BACKEND` unset. Existing uploads/readers continue unchanged. Configure the Render application identity as secret environment values after approval; do not generate an IAM key in a template or commit it.
8. Enable `STOCKCHIEF_IMPORT_BACKEND=aws`, `AWS_REGION`, `STOCKCHIEF_IMPORT_BUCKET` and `STOCKCHIEF_IMPORT_QUEUE_URL` on the Render worker first. This starts its outbox relay, keeps its normal source/document readers, and moves approved execution to AWS. Confirm the AWS worker is ready before enabling direct upload on the web service using the same four values.
9. Test the exact 150,000-row mixed workload end to end, then the million-row and simultaneous cross-tenant workload. Record upload/hash, queue, download, analysis, COPY, apply, verification, web latency and failure/retry timings separately. Compare the same source hashes and database contents before/after.
10. Publish/activate only after the required correctness and hosted performance checks pass. Preserve other chats' later commits; do not deploy this branch over a newer release.

Rollback: stop new direct upload admission; let active handlers drain or recover their leases. Restore Render handling only with the matching code and S3 read access until admitted external sources finish. Database receipts/checkpoints remain the authority. No reversions of customer stock or destructive down-migrations are part of rollback.
